# 网关验证功能使用指南

## 📋 功能概述

网关验证功能确保所有对下游服务的请求都必须经过网关，防止客户端直接访问下游服务，提升系统安全性和可管理性。

## 🔄 工作原理

```
客户端请求 → 网关 (big-gateway/big-gateweb)
                ↓
        注入网关标识请求头
                ↓
        - X-Gateway-Name: 网关名称
        - X-Gateway-Version: 网关版本
        - X-Trace-Id: 链路追踪ID
        - X-Request-From: 请求来源
        - X-Gateway-Timestamp: 时间戳
                ↓
        转发到下游服务
                ↓
下游服务 → GatewayValidationInterceptor 验证请求头
                ↓
        验证通过 → 处理请求
        验证失败 → 返回 403 错误
```

## 🛠️ 组件说明

### 1. 网关层 (big-gateway / big-gateweb)

**文件**: `RequestLogFilter.java`

自动为所有请求注入以下标识头：
- `X-Gateway-Name`: 网关名称（如：big-gateway）
- `X-Gateway-Version`: 网关版本（如：1.0.0）
- `X-Trace-Id`: 唯一追踪ID（格式：网关名称-UUID）
- `X-Request-From`: 请求来源（与网关名称相同）
- `X-Gateway-Timestamp`: 请求时间戳

### 2. 下游服务层 (big-web-common)

**新增文件**:
- `GatewayValidationInterceptor.java`: 网关验证拦截器
- `GatewayValidationProperties.java`: 配置属性类

**修改文件**:
- `WebMvcConfig.java`: 注册拦截器（优先级最高）

## ⚙️ 配置说明

在下游服务的 `application.yml` 中添加以下配置：

```yaml
gateway:
  validation:
    enabled: true                    # 是否启用网关验证
    strict-mode: true                # 严格模式
    required-headers:                # 必须存在的请求头
      - X-Gateway-Name
      - X-Trace-Id
    exclude-paths:                   # 排除的路径
      - /actuator/**
      - /health
      - /swagger-resources/**
      - /v3/api-docs/**
      - /swagger-ui/**
      - /doc.html
```

### 配置项详解

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `enabled` | boolean | false | 是否启用网关验证。开发环境建议关闭，生产环境建议开启 |
| `strict-mode` | boolean | false | 严格模式。true=拒绝所有直接访问（返回403），false=仅记录警告但放行 |
| `required-headers` | List | ["X-Gateway-Name", "X-Trace-Id"] | 必须存在的请求头列表 |
| `exclude-paths` | List | ["/actuator/**", "/health", ...] | 排除的路径，支持 `*` 和 `**` 通配符 |

## 🚀 使用场景

### 场景 1: 开发环境（宽松模式）

```yaml
gateway:
  validation:
    enabled: false  # 关闭验证，方便直接访问下游服务调试
```

**优点**: 开发时可以直接访问下游服务，不需要启动网关

### 场景 2: 测试环境（警告模式）

```yaml
gateway:
  validation:
    enabled: true
    strict-mode: false  # 仅记录警告，不拒绝请求
```

**优点**: 可以发现未通过网关的请求，但不影响测试

### 场景 3: 生产环境（严格模式）

```yaml
gateway:
  validation:
    enabled: true
    strict-mode: true  # 拒绝所有直接访问
```

**优点**: 确保所有请求都经过网关，提升安全性

```

```

```
WARN  请求被拦截 | Status: 403 | Message: 请求必须经过网关 | Path: /api/users
```

### 验证失败（宽松模式）

```
WARN  网关验证失败 | 缺少请求头: X-Gateway-Name | Path: /api/users | IP: 192.168.1.100
WARN  宽松模式：允许直接访问，但不推荐 | Path: /api/users
```

## 🧪 测试方法

### 1. 通过网关访问（正常）

```bash
# 请求经过网关，自动注入标识头
curl http://localhost:8080/example/api/users
```

**预期**: 请求成功，日志显示"网关验证通过"

### 2. 直接访问下游服务（被拦截）

```bash
# 直接访问下游服务，缺少网关标识头
curl http://localhost:8088/web-example/api/users
```

**预期**: 
- 严格模式：返回 403 错误 `{"success":false,"code":403,"message":"请求必须经过网关"}`
- 宽松模式：请求成功，但日志显示警告

### 3. 手动添加网关标识头（模拟网关）

```bash
# 手动添加网关标识头，模拟网关转发
curl -H "X-Gateway-Name: big-gateway" \
     -H "X-Trace-Id: test-123" \
     http://localhost:8088/web-example/api/users
```

**预期**: 请求成功，日志显示"网关验证通过"

## 🔧 高级用法

### 1. 在业务代码中获取网关信息

网关验证通过后，会将网关信息存储到 request attribute 中：

```java
@GetMapping("/api/users")
public Result<List<User>> getUsers(HttpServletRequest request) {
    String gatewayName = (String) request.getAttribute("gatewayName");
    String traceId = (String) request.getAttribute("traceId");
    String gatewayVersion = (String) request.getAttribute("gatewayVersion");
    
    log.info("请求来自网关: {}, TraceId: {}", gatewayName, traceId);
    
    // 业务逻辑...
    return Result.success(users);
}
```

### 2. 自定义排除路径

根据业务需求自定义排除路径：

```yaml
gateway:
  validation:
    exclude-paths:
      - /actuator/**           # 健康检查
      - /health                # 健康检查
      - /api/public/**         # 公开API
      - /webhook/**            # Webhook回调
      - /callback/**           # 第三方支付回调
```

### 3. 多网关支持

如果有多个网关，可以配置不同的网关名称：

```yaml
gateway:
  validation:
    required-headers:
      - X-Gateway-Name
      - X-Trace-Id
```

网关会自动注入自己的名称，拦截器会验证该字段是否存在。

## ⚠️ 注意事项

### 1. 开发环境建议

- **关闭验证**或**使用宽松模式**，方便直接调试下游服务
- 避免频繁启动网关影响开发效率

### 2. 生产环境建议

- **必须开启严格模式**，确保所有请求都经过网关
- 配置合理的排除路径（如健康检查、监控端点）
- 监控日志中的验证失败记录，及时发现异常访问

### 3. 性能影响

- 拦截器性能开销极小（仅检查请求头是否存在）
- 建议在生产环境开启，不会影响系统性能

### 4. 与现有拦截器的关系

拦截器执行顺序：
1. **GatewayValidationInterceptor** (order=0) - 网关验证
2. **TraceIdInterceptor** (order=1) - 链路追踪
3. **RequestLogInterceptor** (order=2) - 请求日志

网关验证拦截器优先级最高，确保在业务处理前完成验证。

## 🐛 故障排查

### 问题 1: 所有请求都被拦截

**原因**: 网关未正确注入请求头

**解决**:
1. 检查网关是否正常运行
2. 检查网关的 `RequestLogFilter` 是否生效
3. 查看网关日志，确认请求头是否注入

### 问题 2: 健康检查被拦截

**原因**: 未正确配置排除路径

**解决**:
```yaml
gateway:
  validation:
    exclude-paths:
      - /actuator/**
      - /health
```

### 问题 3: 宽松模式下仍然被拦截

**原因**: `strict-mode` 配置为 true

**解决**:
```yaml
gateway:
  validation:
    strict-mode: false  # 改为宽松模式
```

## 🎯 总结

网关验证功能通过简单的请求头验证，实现了对下游服务的访问控制：

✅ **安全性**: 防止客户端直接访问下游服务  
✅ **可追溯**: 每个请求都带有 TraceId，便于链路追踪  
✅ **灵活性**: 支持严格/宽松两种模式，适应不同环境  
✅ **可配置**: 支持自定义排除路径和必需请求头  
✅ **高性能**: 拦截器开销极小，不影响系统性能
